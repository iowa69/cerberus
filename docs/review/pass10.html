Summary

Cerberus is written as if every subprocess succeeds, every machine is the machine that ran /proc/meminfo, and nobody ever runs two copies at once. The single most serious defect is that pipe() checks only the last command's exit status, so an aligner that dies half-way through — OOM-kill, I/O error, corrupt index — produces a structurally valid BAM containing a fraction of the reads, and the pipeline proceeds to completion reporting success; I reproduced this with real minimap2/samtools, losing 1498 of 2000 records with samtools quickcheck reporting the BAM as healthy. Resource detection is host-wide rather than allocation-aware: os.cpu_count() still returns 24 under taskset -c 0,1, and _detect_memory_gb() still returns 27 inside a 2 GiB cgroup, which then becomes bbduk.sh -Xmx27g — I measured the JVM accepting MaxHeapSize = 28,991,029,248 in that cgroup and dying by SIGKILL (exit 137), where letting the JVM alone would have produced a clean, catchable OutOfMemoryError. Nothing anywhere checks that the machine can hold the 11 GB Kraken2 DB, and because GDPR is the last stage, that discovery happens roughly 15–30 hours into a 50 GB --all run. Disk is modelled at ~576 GB peak and ~409 GB permanently resident for a 50 GB input (11.5× and 8.2×), against a README that promises "~2× input FASTQ size during processing; cleaned automatically" — there is no cleanup code, and no --tmpdir. Finally, two runs sharing a --ref-dir is genuinely unsafe: cleanup_partial() unconditionally deletes another run's in-flight 11 GB download, and archive assets are never hash-verified, so a half-extracted Kraken2 DB reads as "present and verified" to both ensure() and doctor, and --update-refs cannot repair it.

Verified working

  • No log-path collisions across modes or stages — instrumented --all dry run emitted 29 tool invocations; every log_path was unique. logs/{meta,profiling,gdpr_meta,gdpr_profiling}/ keeps the four mode namespaces apart (orchestrator.py:86, gdpr.py:45-47), and tags are distinct within each. run()'s mode="w" (shell.py:71) therefore never destroys a sibling stage's log.
  • Large BAM intermediates are deleted promptly — align.py:84-85, 129-130, 183-184, 225-226 unlink each .bam right after samtools fastq + flagstat, keeping the two ~52 GB alignment BAMs from ever coexisting.
  • Downloaded non-archive assets are integrity-checked before being published — refs.py:158-170 verifies SHA256 on the .tmp and only then tmp.rename(target), an atomic same-directory rename. A mismatch deletes the file (refs.py:160-165).
  • **run() fails loudly and points at the evidence** — shell.py:84-87 raises ToolError carrying the command, rc, and log path.
  • A corrupt Kraken2 DB fails loudly rather than silently mis-classifying — fed a garbage hash.k2d/taxo.k2d/opts.k2d, kraken2 exits 65 (classify: malformed taxonomy file), which run(check=True) converts into a ToolError.
  • Re-running after a crash overwrites stale bbduk outputs rather than appending to them — tested bbduk.sh against a pre-existing truncated out= file: exit 0, output correctly replaced (104 bytes). No ow=t needed.
  • **pipe() manages pipe file descriptors correctly on the happy path** — shell.py:128-130 closes the parent's copy of each upstream stdout after handing it to the next child, so there is no fd leak and no SIGPIPE-never-arrives deadlock in normal operation.
  • Empty-stream guards prevent cascading crashes — kmer.py:52-54, 94-102 short-circuit bbduk on empty input and emit valid empty gzip; kraken.py:141-147 and kraken.py:175-179 emit placeholders rather than letting a FileNotFoundError escape.
  • fastp and fastplong thread counts are capped — qc.py:62 (min(cfg.threads, 16)) and qc.py:112 (min(cfg.threads, 8)) correctly recognise that these tools do not scale past those points.
  • The JSONL run log is opened in append mode — logger.py:61 uses mode="a", so a re-run into the same -o directory preserves the previous run's structured history.
  • Final outputs are published by atomic rename — meta.py:79-80, gdpr.py:78-79, long_read.py:43 use Path.replace(), which is atomic within a filesystem, so a reader never sees a half-written final file (the profiling path is the exception; see F7).
  • **--threads is range-checked** — orchestrator.py:55-56 rejects < 1 before any work starts.

Findings

critical F1. pipe() ignores the exit status of every command except the last — silent, undetectable data loss

location
cerberus/utils/shell.py:132-140
what
pipe() runs for p in procs: p.wait() and then inspects only procs[-1].returncode. There is no pipefail equivalent. Every alignment in Cerberus is pipe([aligner, samtools_view]) — 8 of the 29 invocations in an --all run (align.py:64, 121, 169, 217). If the aligner dies, samtools view sees a clean EOF on a record boundary, writes a well-formed BAM of whatever it received, and exits 0. Cerberus records success.
trigger
minimap2 or bowtie2 terminating non-zero or by signal part-way through: OOM-kill (F2 makes this the expected outcome), an ENOSPC on a temp file, a truncated .mmi/.bt2 index (F4 makes that the expected outcome), a transient NFS read error on the input FASTQ, or a preemption signal. Also samtools fastq is unaffected — the corruption is already baked into the BAM.
consequence
Reproduced with real tools. minimap2 -ax sr | samtools view -b -o trunc.bam -, with minimap2 exiting 1 after emitting 505 lines: pipe() returned ToolResult(returncode=0), raised nothing; the BAM held 502 of 2000 records; samtools quickcheck -v returned rc=0 with no complaint. The run continues through entropy filtering, concatenation, GDPR, accounting, and prints Cerberus finished in Xs. The delivered FASTQ is missing 75% of the sample, accounting.tsv reports the reduced count as a genuine biological result, and the loss is attributed to host removal. For a decontamination tool whose entire value proposition is auditable read accounting, this is the worst possible failure mode: wrong numbers, presented confidently, with no error anywhere in any log.
fix
In pipe(), collect [p.wait() for p in procs] and raise ToolError if any element is non-zero, naming the offending command and distinguishing signals (rc < 0) from exits. Additionally, on failure of any stage, terminate the remaining children (p.kill()) rather than leaving them to drain. Consider also passing samtools quickcheck over each BAM before consuming it, and cross-checking flagstat's total against the input read count — the flagstat file is already being written (align.py:81-82) and is currently never read by anything.

critical F2. No memory preflight, and -Xmx computed from /proc/meminfo disables the JVM's own container-awareness

location
cerberus/cli.py:29-39, cerberus/stages/kmer.py:64,110, cerberus/stages/entropy.py:40,70, cerberus/stages/kraken.py:52-68,104-115
what
Three independent problems compound. (a) _detect_memory_gb() reads MemTotal from /proc/meminfo, which is not namespaced by cgroups. Under a memory cgroup it reports the host's RAM. (b) That number is passed verbatim as bbduk.sh -Xmx{cfg.memory_gb}g (kmer.py:64) and -Xmx{max(2, memory_gb//2)}g (entropy.py:40). Setting -Xmx explicitly overrides the JVM's MaxRAMPercentage container detection, which would otherwise have read the cgroup limit and got it right for free. (c) Kraken2 receives no memory flag at all — no --memory-mapping, no cap (kraken.py:52-68). It loads the entire DB into RAM. The manifest declares that DB at 11,048,814,212 bytes compressed (data/default_manifest.json), and the README itself says "~14 GB extracted". Nothing in the codebase reads size_bytes, compares anything to available RAM, or warns.
trigger
Any SLURM/LSF/Kubernetes job with a memory limit, any Docker container, or any laptop smaller than the DB. Measured on this host: inside systemd-run -p MemoryMax=2G, _detect_memory_gb() returned 27.
consequence
Measured directly. With -Xmx27g inside a 2 GiB cgroup the JVM reports MaxHeapSize = 28991029248 and is SIGKILLed by the kernel (exit 137); with no -Xmx at all in the same cgroup the JVM computes MaxHeapSize = 536870912 and produces a clean, catchable java.lang.OutOfMemoryError (exit 1). So the explicit flag converts a recoverable, diagnosable error into an opaque kill. The timing makes it far worse: from the instrumented trace, kraken2 is invocation #18 of 29, running only after fastp, both minimap2 passes, bowtie2 --very-sensitive-local, and three bbduk passes have completed — on a 50 GB --all run that is roughly 15–30 hours of compute before the first byte of the DB is touched. An OOM-kill of kraken2 surfaces as ToolError (rc 137); an OOM-kill of the Python parent (the kernel picks by oom_score, not by who allocated) surfaces as nothing at all. The README's "RAM (peak) ~9 GB on --gdpr step (Kraken2)… Designed for 16 GB laptops" contradicts the README's own "~14 GB extracted" DB size two sections earlier, and --memory NG is documented as a "bbduk/Kraken2 memory cap" when it never reaches Kraken2.
fix
Read /sys/fs/cgroup/memory.max (v2) and /sys/fs/cgroup/memory/memory.limit_in_bytes (v1) and take the minimum with MemTotal. Stop passing -Xmx and let the JVM's container detection work, or cap it at ~70% of the detected allocation. Preflight the GDPR requirement before stage 1: du -sb the extracted Kraken2 DB (or use the manifest size_bytes) and refuse to start, or downgrade to --memory-mapping, if it does not fit. Correct the README table.

high F3. Peak disk is ~11.5× input, nothing under _work/ is ever deleted, and there is no --tmpdir

location
cerberus/config.py:122-136, cerberus/orchestrator.py:59-103, cerberus/stages/kraken.py:48-70
what
work_dir is hard-wired to out_dir/_work — there is no --tmpdir, so scratch cannot be pointed at node-local NVMe and always lands next to the deliverables. ensure_directories() creates it; nothing ever removes it. Grep for rmtree/cleanup across cli.py and orchestrator.py returns nothing. --keep-intermediates only gates the BAM unlinks and bbduk outm= files (align.py:84, kmer.py:58-59); it does not control _work/ retention. There is also no free-space check anywhere (no shutil.disk_usage, no statvfs).
trigger
Any run. Modelled on the verified file inventory from the instrumented --all dry run (26 distinct _work/ artefacts), for a 50 GB paired input at 3.8× gzip, 95% QC retention, 95% non-host (the low-host-fraction case that maximises disk).
consequence
~576 GB peak, ~409 GB permanently resident. The dominant terms are the ones the design never accounts for: - kraken2 --unclassified-out writes plain, uncompressed FASTQ (kraken.py:48,100) — a transient ~167 GB spike per GDPR branch before _gzip_inplace compresses it; - kraken2 --output (kraken.py:50,102) writes one --use-names line per read, ~85 bytes, to ~22 GB per invocation × 2 = 44 GB of per-read text that nothing in Cerberus ever reads and that is never compressed or deleted; - the profiling chain retains four full copies of the read set (02_bowtie2.unmapped 43.8 GB, 03_bbduk_kmer.kmerclean 43.6 GB, 04_entropy.entropy 42.7 GB, plus the 44 GB final), because unlike meta it builds its final by concat_gz copy rather than Path.replace move (profiling.py:145 vs meta.py:79). The README states "Disk (run) | ~2× input FASTQ size during processing; cleaned automatically unless --keep-intermediates". Both clauses are false: measured 11.5×, and there is no cleanup path in the codebase. A user following the README will size a scratch allocation at 100 GB and hit ENOSPC around invocation 10 of 29. Separately, ref_dir settles at ~41 GB, not the documented ~13 GB, because _extract (refs.py:206-223) never deletes the .tar.zst after extracting it — both the 11.05 GB Kraken2 tarball and the 3.79 GB bowtie2 tarball are kept forever alongside their extracted contents, in ~/.cerberus/refs/, i.e. inside the quota'd home directory on most clusters.
fix
Add --tmpdir defaulting to $TMPDIR. Delete each stage directory once the next stage's output is verified, or add --cleanup {none,intermediate,all} defaulting to removing _work/ on success. Pass --output - to kraken2 to suppress the per-read TSV (only --report is consumed). Stream kraken2's unclassified output through pigz instead of materialising plain FASTQ. unlink() the tarball after successful extraction. Preflight shutil.disk_usage(work_dir) against a size estimate derived from the input and refuse to start if short. Correct the README.

high F4. Two runs sharing a --ref-dir corrupt each other; archive assets are never integrity-checked and cannot be repaired

location
cerberus/refs.py:238-244 (cleanup_partial), cerberus/refs.py:121-129 (is_satisfied), cerberus/orchestrator.py:64, cerberus/refs.py:131-146 (ensure)
what
There is no lock file anywhere (grep for flock/fcntl/lock finds only zenodo_upload.py). orchestrator.py:64 calls cleanup_partial(cfg.ref_dir) at the start of every run, which globs *.tmp and unlinks unconditionally with no age check and no ownership check. Separately, is_satisfied() for archive assets returns target.is_dir() and any(target.iterdir()) — a non-empty directory is sufficient; the SHA256 in the manifest is never used for the two tarballed assets, which are also the two largest and the two that matter most (the Kraken2 GDPR DB and the bowtie2 index).
trigger
The default --ref-dir is ~/.cerberus/refs, shared by every job a user submits. Two array tasks starting within the ~10-minute window of an 11 GB download, or within the extraction window, is the ordinary case, not the exotic one.
consequence
Both races reproduced.
fix
Take an exclusive fcntl.flock on <ref_dir>/.lock (or a per-asset lock) around the ensure/download/extract sequence, with a wait-and-retry rather than a failure. Extract into <name>.tmp.<pid>/ and os.rename the directory into place atomically. Verify the tarball's SHA256 before extracting and write a .verified sentinel containing the hash; make is_satisfied() for archives require that sentinel. Make cleanup_partial skip .tmp files modified within the last N minutes, and make --update-refs actually force (ensure(..., force=True)).

high F5. Tool availability is checked at stage entry, hours into a run; there is no preflight, and --dry-run cannot serve as one because it crashes

location
cerberus/utils/shell.py:38-44, cerberus/stages/kmer.py:49, cerberus/stages/kraken.py:45, cerberus/autotune.py:115, cerberus/cli.py:236-285
what
require_tools is called inside each stage function. bbduk.sh is first demanded at kmer.py:49 / entropy.py:31 — invocation #8 in an --all run, after both minimap2 passes. kraken2 is first demanded at kraken.py:45 — invocation #18, after everything else has finished. cerberus doctor exists but is never invoked automatically (no call site outside cli.py:293), and nothing in orchestrator.run() validates the toolchain up front.
trigger
A conda environment that resolved without bbmap, a module load that was omitted from the batch script, a $PATH that differs between the login shell and the compute node — the single most common cluster failure there is.
consequence
The user spends 15–30 hours in minimap2 and bowtie2 and is then told Missing required tool(s): kraken2. All GDPR outputs are absent, ~400 GB of _work/ is left behind, and there is no resume (F7), so the fix is to install the tool and repeat the entire 30 hours. The obvious workaround is unavailable: **--dry-run is broken.** Running the real CLI with --dry-run on the short-read path crashes at autotune.py:115 with an unhandled FileNotFoundError — dry-run never produces fastp.json, and autotune_from_fastp opens it without a guard. It also still requires all 23 GB of references to be present (orchestrator.py:75 runs before any stage), so it cannot preflight a fresh machine at all. doctor's tool list is also wrong in both directions: it marks **seqkit as required** and exits 1 without it, though Cerberus never invokes seqkit; while zcat (qc.py:120, fastq.py:22), tar (refs.py:219), cat and wc are invoked but never checked.
fix
Compute the union of tools the selected modes will need and require_tools(*that) in orchestrator.run() before refs.ensure(). Guard autotune_from_fastp so --dry-run returns TunedParams() when the JSON is absent. Skip refs.ensure() under --dry-run (or reduce it to a report). Fix the doctor lists, and run the equivalent check automatically at run start.

high F6. Thread counts are host-wide, not allocation-aware, and every pipe double-books the CPU budget

location
cerberus/cli.py:86, cerberus/stages/align.py:56+63, 114+120, 162+168, 212+216
what
The --threads default is os.cpu_count(), which reports the machine's CPU count regardless of CPU affinity or cgroup quota. That one number is then passed to both halves of every pipe: minimap2 -t N | samtools view -@ N. Nothing is capped outside fastp/fastplong.
trigger
Any scheduler that gives you a share of a node — the normal case. Verified: under taskset -c 0,1, os.cpu_count() returned 24 while len(os.sched_getaffinity(0)) returned 2.
consequence
Measured with real tools: cfg.threads=12 produced 31 concurrent OS threads (minimap2 peak 16, samtools peak 15) for a single stage — 2.6× the requested allocation. On a SLURM --cpus-per-task=4 task on a 128-core node, Cerberus defaults to -t 128 and spawns ~263 runnable threads inside a 4-CPU cpuset: context-thrashing, ~30× wall-clock inflation, and on many sites an automatic kill for exceeding the CPU allocation. With -t 128 there are second-order costs too — minimap2's per-thread batch buffers multiply, samtools view -@ 128 allocates 128 BGZF compression buffers to write a single BAM, bbduk threads=128 splits a fixed -Xmx heap across 128 workers and drives GC, and kraken2 stops scaling past ~16–32 threads while each thread holds a work buffer.
fix
Default to len(os.sched_getaffinity(0)) (or os.process_cpu_count() on 3.13+), further clamped by /sys/fs/cgroup/cpu.max. Split the budget across a pipe rather than duplicating it — e.g. aligner gets max(1, N-2), samtools view gets min(4, N), which is where its scaling flattens anyway. Cap kraken2 at ~32.

medium F7. No checkpointing, no --resume, and the final-output unlink() destroys a good previous result before the new one exists

location
cerberus/pipelines/profiling.py:139-145, cerberus/pipelines/meta.py:76-77,91, cerberus/pipelines/gdpr.py:75-76,126, cerberus/utils/fastq.py:11-36
what
There is no state file, no stage-completion marker, and no --resume (grep finds none). A run that dies at stage 5 of 8 leaves _work/ populated with a mixture of complete and truncated outputs, indistinguishable from one another, and a re-run redoes everything from fastp. Separately, profiling.py:139 calls final.unlink(missing_ok=True) and only then begins a concat_gz that streams ~44 GB — a destructive window of minutes during which the previous good result no longer exists and the new one is incomplete. (meta.py and gdpr.py have the same pattern but a microsecond window, since the replacement already exists on disk.)
trigger
ENOSPC (made likely by F3), preemption, node failure, or any exception, during the profiling concat of a re-run.
consequence
Reproduced end-to-end. A previous good S.profiling.fastq.gz (40,000 reads) was deleted by line 139; the write then failed with OSError [Errno 27]; what remained on disk was a 150,000-byte truncated gzip at the exact final output path, which file(1) identifies as "gzip compressed data" and which **count_reads() reports as 59,478 reads with no error and no exception**. Only gzip -t (rc=1) reveals the corruption, and Cerberus never runs it. count_reads (fastq.py:29-36) spawns pigz -dc | wc -l and checks neither process's return code, so the accounting layer will confidently publish a fabricated number for a corrupt file. This is precisely the "truncated output that looks valid" case. The raw OSError is also not caught by cli.py:316-324.
fix
Write to final.partial and Path.replace() into position only on success — never unlink the old result first. Check the return codes in _line_count_pipe. Emit a per-stage .done sentinel containing the output's size and read count, and add --resume that skips stages whose sentinel matches. Validate each gzip output (pigz -t, or check for the final empty deflate block) before treating a stage as complete.

medium F8. run() accepts a timeout that no caller ever passes, and pipe() cannot time out at all

location
cerberus/utils/shell.py:54,80, cerberus/utils/shell.py:90-140
what
run() threads a timeout through to subprocess.run. Grep across the whole repository: the only two occurrences of the word are the parameter declaration and its use — no call site anywhere passes it. pipe() has no timeout parameter at all, and p.wait() (shell.py:133) blocks unbounded.
trigger
A hung NFS read on the 7.7 GB .mmi; aria2c stalled on a Zenodo connection that neither completes nor resets; bowtie2 spinning on a corrupt index; a downstream process in a pipe that stops reading, blocking the upstream at 64 KB of pipe buffer.
consequence
The pipeline hangs forever with no diagnostic. On a cluster it burns the full walltime allocation and is killed by the scheduler with no useful log; interactively it looks like slow progress, since the per-stage log file has already been written with the # CMD: header and simply stops growing. Nothing detects the absence of progress.
fix
Either delete the dead parameter or use it. A per-stage timeout with a sane default, plus a watchdog on output-file growth, would convert an indefinite hang into a ToolError naming the stalled command. pipe() needs the same treatment, applied to the whole chain.

medium F9. Ctrl-C and SIGTERM leave child processes orphaned; there is no signal handling at all

location
cerberus/cli.py:322-324, cerberus/utils/shell.py:107-135
what
Grep for signal, atexit, SIGTERM, SIGINT, terminate, kill across cerberus/ returns nothing. cli.py:322 catches KeyboardInterrupt, prints "Interrupted.", and returns 130; the Popen objects held in pipe()'s local procs list are never terminated, and pipe()'s finally block closes only the log file handle.
trigger
Ctrl-C; scancel; a supervisor or workflow engine (Nextflow, Snakemake, timeout) signalling the Python PID; any exception unwinding through pipe() while children are alive.
consequence
Reproduced. A pipe() blocked in p.wait() received SIGINT on the parent PID only; the parent printed "Interrupted." and exited 130; both children were reparented to PID 2691 and continued running, still carrying the dead parent's PGID. In production those two processes are minimap2 -t 32 holding the 7.7 GB index and 32 threads, and samtools view -@ 32 still appending to a BAM that nobody will ever consume — burning a full node's CPU indefinitely, invisible to the scheduler's accounting for the now-dead job. Interactive Ctrl-C in a TTY happens to escape this, because the terminal driver signals the whole foreground process group and the children inherit it — but that is accidental, not designed, and it does not hold for nohup, detached tmux, batch jobs, or programmatic signals. There is also no SIGTERM handler whatsoever, so a scheduler's grace-period SIGTERM kills Python instantly with no cleanup of the partial final output described in F7.
fix
Track live Popen handles in a module-level registry; install SIGINT/SIGTERM handlers and an atexit hook that terminate()s then kill()s them. Add try/finally in pipe() that reaps children on any exception. Launching children with start_new_session=True and signalling the group explicitly makes the behaviour deterministic instead of TTY-dependent.

low F10. Most failure modes surface as raw Python tracebacks rather than actionable errors

location
cerberus/cli.py:316-324
what
main() catches exactly two exception types: ConfigError and KeyboardInterrupt. Everything else propagates to the interpreter.
trigger
Missing references (RefManagerError), any failed tool (ToolError), a missing tool (RuntimeError from require_tools), disk exhaustion (OSError), a missing bowtie2 index (FileNotFoundError from profiling.py:167), a missing Kraken2 DB (FileNotFoundError from gdpr.py:139), and the ref-dir race in F4.
consequence
Verified: cerberus ... --all --dry-run --no-auto-download on a fresh ref-dir prints a nine-line traceback ending in cerberus.refs.RefManagerError: Asset 'masked_t2t_hla_minimap2' missing and --no-auto-download set. The message itself is good; the traceback around it makes a routine, expected condition look like a crash, and buries the remediation line in stderr noise. Exit codes are also undifferentiated — everything is 1 — so a wrapper script cannot distinguish "missing input" from "tool crashed" from "out of disk".
fix
Catch ToolError, RefManagerError, and OSError in main(); print the message plus the relevant log path; return distinct exit codes (2 config, 3 missing refs, 4 tool failure, 5 resource exhaustion). Keep the traceback behind --verbose.

low F11. tarfile.extractall(filter="data") requires Python ≥ 3.10.12 / ≥ 3.11.4, but requires-python = ">=3.10"

location
cerberus/refs.py:212, pyproject.toml:10, environment.yml, conda-recipe/meta.yaml
what
The filter keyword arrives with PEP 706 in Python 3.12 and was backported only to the June-2023 security releases (3.11.4, 3.10.12, 3.9.17, 3.8.17). pyproject.toml, environment.yml, and conda-recipe/meta.yaml all declare >=3.10, which admits 3.10.0–3.10.11 and 3.11.0–3.11.3.
trigger
Installing on an interpreter in those ranges. Debian 12 (bookworm) ships Python 3.11.2; RHEL 9's python3.11 is also 3.11.2; Ubuntu 22.04 shipped 3.10.6.
consequence
Verified across real interpreters: **3.10.11 → TypeError: TarFile.extractall() got an unexpected keyword argument 'filter'; 3.10.12 → OK; 3.11.3 → no filter parameter in the signature**; 3.12 → OK. In practice the blast radius is small, because both shipped archives are .tar.zst and _extract's dispatch (refs.py:210-221) routes those through the external zstd | tar pipe, never reaching tarfile. The tarfile branch is only taken for .tar, .tar.gz, or .tar.xz — i.e. a user-supplied or future manifest. So this is a latent crash on a currently-unexercised path, not a live one, but the metadata is wrong regardless and a pip install on Debian 12 advertises support it does not have.
fix
Set requires-python = ">=3.10.12" (or >=3.11.4), or guard with sys.version_info >= (3, 10, 12) and fall back to plain extractall() with a manual member check. Mirror the constraint in environment.yml and the conda recipe.

low F12. The reference cache grows to ~41 GB in $HOME and fetch-refs downloads an asset no pipeline uses

location
cerberus/refs.py:206-223 (_extract), cerberus/refs.py:225-227 (fetch_all), cerberus/refs.py:37-45 (_PIPELINE_TO_ASSETS), cerberus/config.py:15
what
_extract never deletes the source tarball after a successful extraction, so both the 11.05 GB kraken2_gdpr_compact.tar.zst and the 3.79 GB masked_t2t_hla_bt2.tar.zst remain alongside their unpacked contents forever. fetch_all() iterates the entire manifest rather than the union of _PIPELINE_TO_ASSETS, so it also pulls human_kmer_set (0.93 GB), which appears in no pipeline mapping and is referenced nowhere in the code. DEFAULT_REF_DIR is ~/.cerberus/refs.
trigger
cerberus fetch-refs, or any first run.
consequence
Computed from the manifest: 23.47 GB downloaded, settling at ~41.5 GB resident (7.70 mmi + 3.79 + ~4.0 bt2 + 11.05 + ~14 k2 + 0.93 k27), against a README claim of "~13 GB extracted". On clusters where $HOME carries a 20–50 GB quota — the norm — this either fails outright mid-extraction or consumes the user's entire allowance. Roughly 16 GB of the total is pure redundancy.
fix
unlink() the tarball after _extract succeeds (behind --keep-archives if desired). Have fetch_all() fetch only assets reachable from _PIPELINE_TO_ASSETS, or drop human_kmer_set from the manifest. Default ref_dir to $XDG_CACHE_HOME or $CERBERUS_REFS and document the real footprint.
One of ten independent review passes over Cerberus v0.1.1. Findings were verified by executing the pipeline against miniature synthetic references before being acted on. Back to the index.
