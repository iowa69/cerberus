# v0.2.0 review A — new-bug hunt in the changed code

Scope: `git diff 125a656..HEAD -- cerberus/`, lens on `utils/shell.py`, `stages/align.py`,
`stages/concat.py`, `utils/fastq.py`, `pipelines/*.py`. All claims below were reproduced against
the real toolchain (`.cenv`) and the miniature fixture set; scratch artefacts are under
`/home/iowa/Desktop/cerberus/work/rev2a/`. Note: the working tree carries an *uncommitted* edit to
`cerberus/pipelines/gdpr.py` (GDPR output naming for the profiling head) that landed while this
review was in progress; findings below reflect the working tree, not HEAD.

## Summary

The refactor is broadly sound and the science-facing parts are correct: pair-level `both`/`either`
filtering does exactly what the new docstring claims, the mate-tagged merge produces valid
multi-member gzip with no duplicate read IDs, `pipe()` really does catch upstream failures the old
code missed, and `publish()` genuinely fixes the "a `--dry-run` deletes your last real run"
bug. The specific hazards the brief asked about in `pipe()`'s `finally` — a live process being
killed on the success path, a return code read early, `_LIVE` leaking — do **not** exist; I could
not provoke any of them. The worst thing I found is elsewhere in the same file: the new
`terminate_all()` teardown, whose docstring promises to "tear down the whole process group",
signals only direct children, so a Ctrl-C/SIGTERM leaves the `bbduk.sh` JVM (`-Xmx27g` on a default
run) orphaned and still writing into `_work/` while the CLI prints "Stopped 1 running tool(s)" —
reproduced with a real bbduk run. Close behind: `pipe()` now systematically blames the *wrong tool*
when a downstream stage fails (the upstream's SIGPIPE shadows the real error), which is a
diagnostic regression relative to v0.1.1; `count_reads()`'s new fallback turns a corrupt `.gz` into
an unhandled `EOFError` that kills an otherwise-successful run; and `StageTracker.record()` +
the report now perform ~66 full decompression passes per `--all` run against ~13 in v0.1.1.

## Verified working

- **`pipe()` success path does not kill anything, and reads no return code early** — every
  process is waited before the `finally` runs, so `p.poll()` is never `None` there. Exercised
  3-stage + `final_stdout`, 2 M lines through 3 stages, 500 MB through `gzip -c` to
  `final_stdout` (82 KB/2 000 000 lines round-tripped intact), and a large-data run with the last
  stage on `DEVNULL`. `cerberus/utils/shell.py:241-249`.
- **`_LIVE` does not leak across any exception path** — checked `len(_LIVE)` after: success,
  failing first stage, failing middle stage, failing last stage, `FileNotFoundError` from a missing
  binary mid-pipe, pipe timeout, and `run()` timeout. Zero in all nine cases.
  `cerberus/utils/shell.py:241-249`.
- **`p.stdout.close()` in the `finally` cannot mask a real error** — for every non-final stage the
  handle is already closed by `prev_stdout.close()` at spawn time
  (`cerberus/utils/shell.py:224-225`), and the final stage has `p.stdout is None`
  (`DEVNULL`/file). The guarded `not p.stdout.closed` test never fires in practice.
- **`run(stdout_path=...)` keeps stderr in the log and stdout clean, with correct handle
  ordering** — `# CMD:` header is written and flushed before `Popen`
  (`cerberus/utils/shell.py:136-138`); verified log contains only `# CMD:` + `TO_STDERR`, and
  `stdout_path` contains only `TO_STDOUT`. Also verified on the failure path (`rc=4`, stderr
  `BOOM` present in the log). `cerberus/utils/shell.py:139-159`.
- **Timeout kills the tracked child** — `run(timeout=2)` and `pipe(timeout=2)` both return in
  2.00 s with `rc=-9`; the direct child is gone. (Grandchildren are not — see F1.)
  `cerberus/utils/shell.py:148-153`, `:229-239`.
- **`concat_mate_tagged()` produces valid gzip and preserves record counts** — end-to-end
  `--all` run: 4 000 surviving pairs → `S1.profiling.fastq.gz` with exactly 8 000 records,
  4 000 `/1` + 4 000 `/2`, **0 duplicate read IDs**, `pigz -t` clean. Unit-level: empty gzip member
  input (0 records, valid output), missing trailing newline on the last record (healed by awk's
  `print`), Casava comment stripped (`@x 1:N:0:ATC` → `@x/1`), `.part*` temp files cleaned on the
  success path. `cerberus/stages/concat.py:104-131`.
- **`count_reads()` magic-byte detection is right** — gzip named `.fastq` (3), plain text named
  `.gz` (7), multi-member gzip (20), valid empty gzip member (0), zero-byte file (0), and a
  non-multiple-of-4 file (warns "looks truncated", reports 1). `cerberus/utils/fastq.py:28-60`.
- **Pair-level filtering is correct for both strategies** — `half.*` fixture (1 000 pairs with a
  host R1 + 1 000 fully clean pairs; bowtie2 flagstat confirms exactly 1 000 mapped):
  `--meta` (`both`) kept 2 000 pairs, `--profiling` (`either`) kept exactly the 1 000 clean pairs.
  `cerberus/stages/align.py:74-88`, `:151-196`.
- **`publish()` no longer lets a dry-run destroy a previous real run** — dry-run `--all` into a
  directory holding real outputs left `S1.meta.R1.fastq.gz` byte-identical (md5 unchanged). This
  is a genuine fix over v0.1.1's unconditional `unlink(missing_ok=True)`.
  `cerberus/pipelines/base.py:37-51`.
- **`_clean_work_dir()` ordering is correct** — it runs after `accounting.write()`
  (`orchestrator.py:173`) and after `write_run_report()` (`:184`), and is skipped on any exception
  from the pipeline itself. No output is published after it. `cerberus/orchestrator.py:191-192`.
- **`publish()` cross-filesystem `EXDEV` is not reachable by default** — `work_dir` is
  `out_dir/_work` (`config.py:139-141`), so `src.replace(dst)` is always intra-filesystem unless
  the user symlinks `_work` elsewhere.
- **No output is left unpublished in `_work/`** — traced every `AlignOutputs`/`EntropyOutputs`
  producer in meta, profiling, long-read and GDPR; every deliverable path reaches exactly one
  `publish()` call, and no path publishes twice.

## Findings

### F1. `terminate_all()` orphans the real worker process (bbduk JVM survives Ctrl-C/SIGTERM)
- **Severity:** high
- **Location:** `cerberus/utils/shell.py:44-62` (and `cerberus/cli.py:378-396`)
- **What:** The module docstring claims "All spawned children are tracked so a Ctrl-C tears down
  the whole process group instead of leaving a 32-thread aligner running detached." There is no
  process group: `Popen` is never given `start_new_session=True` and `terminate_all()` uses
  `p.send_signal(sig)` / `p.kill()`, which reach only the immediate child. `bbduk.sh` is a bash
  wrapper that ends in `eval $CMD` — the JVM is a *grandchild*. The same limitation applies to the
  timeout kills at `shell.py:150` and `shell.py:234-237`.
- **Trigger:** Reproduced: ran `shell.run()` on a real `bbduk.sh` entropy pass over a 680 MB input
  and called `terminate_all()` after 3 s. `run()` raised `ToolError (rc=-15)` and the handler
  reported "signalled 1", but `ps` still showed
  `java ... -Xmx4g ... bbduk.BBDukS in=big4.fq.gz out=.../bb.out.fq.gz` alive and running. A tty
  Ctrl-C happens to work (the terminal delivers SIGINT to the whole foreground group); `kill <pid>`,
  a scheduler SIGTERM, and the `timeout=` paths do not.
- **Consequence:** After a "clean" interrupt the CLI prints "Stopped N running tool(s)" and exits
  while a multi-GB JVM keeps running and keeps writing into `_work/`. On a shared/cluster node
  that is a resource leak; worse, if the user immediately re-runs into the same `--out-dir` the
  orphan and the new run write the same intermediate paths, silently corrupting the second run's
  inputs. This is precisely the failure mode the new code advertises that it fixes.
- **Fix:** Pass `start_new_session=True` to every `Popen` in `run()`/`pipe()`, then in
  `terminate_all()` (and both timeout kill paths) use
  `os.killpg(os.getpgid(p.pid), sig)` with a `ProcessLookupError` guard, falling back to
  `p.send_signal(sig)`. Escalate to `SIGKILL` on the group after the grace period.

### F2. `pipe()` names the wrong stage whenever a downstream tool fails
- **Severity:** medium
- **Location:** `cerberus/utils/shell.py:256-259`
- **What:** The new per-stage check loops `for i, (cmd, rc) in enumerate(zip(cmds, codes))` and
  raises on the **first** non-zero status. When a downstream stage dies, the upstream producer is
  killed by SIGPIPE and reports `rc=-13`, so stage 1 is always the first non-zero entry and the
  real culprit is never mentioned. The docstring at `:250-254` acknowledges SIGPIPE but treats it
  as a reportable failure rather than as a symptom.
- **Trigger:** Reproduced with real tools:
  `pipe([minimap2 ..., samtools view -b -o /nonexistent_dir_xyz/out.bam -])` →
  `ToolError: Command failed (rc=-13) [stage 1/2: minimap2]: minimap2 -ax sr ...`.
  The step log correctly shows `samtools view: failed to open ... for writing`, but the exception
  the user sees (and the CLI prints, `cli.py:454-456`) blames minimap2.
- **Consequence:** Diagnostic regression against v0.1.1, which reported `procs[-1]` and would have
  named `samtools view` — i.e. exactly right for the most common real failure (downstream tool
  fails: out of disk, bad path, bad reference). Users will chase the wrong tool. `ToolResult`
  carries the full `returncodes` list, but the raised error does not.
- **Fix:** Split the check: report the last non-zero status first, and only fall back to an
  upstream stage when no downstream stage failed. Concretely, ignore `rc in (-13, 141)` for
  stage `i` when any stage `> i` also failed, and include the whole `codes` list in the
  `ToolError` message either way.

### F3. `terminate_all()` re-enters `Popen.wait()` from the signal handler — 10 s stall per child, and a latent self-deadlock
- **Severity:** medium
- **Location:** `cerberus/utils/shell.py:44-62`, called from `cerberus/cli.py:386-390`
- **What:** The SIGINT/SIGTERM handler runs *in the main thread*, which at that moment is almost
  always blocked inside `p.wait()` in `run()`/`pipe()` and therefore already holds that `Popen`'s
  non-reentrant `_waitpid_lock`. `terminate_all()` then calls `p.wait(timeout=10)` on the same
  object; CPython's timed path polls the lock non-blockingly and can never acquire it, so it spins
  for the full 10 s before `TimeoutExpired` lets the code fall through to `p.kill()`. Separately,
  `terminate_all()` takes `_LIVE_LOCK` (`:46`); if the signal lands while the main thread is inside
  `_track`/`_untrack` holding that same lock, the handler blocks forever with no timeout.
- **Trigger:** Reproduced: SIGTERM delivered to a process blocked in
  `pipe([["bash","-c","sleep 60"],["cat"],["cat"]])` — handler logged
  `terminate_all signalled 3 in 10.00s`, and `KeyboardInterrupt` reached `main` only after 12.00 s.
- **Consequence:** Ctrl-C looks like a hang for at least 10 s (longer with several blocked
  children), which invites a second, harder signal — leaving even more orphans (F1). The
  `_LIVE_LOCK` re-entry is a rare but unbounded hang.
- **Fix:** Do not call `Popen.wait()` from the handler. Signal the process groups and return
  immediately; let the already-blocked `p.wait()` in the main thread reap them, and do the
  escalation-to-`SIGKILL` in a normal (non-handler) context. Use a lock-free snapshot of `_LIVE`
  (e.g. `list(_LIVE)` guarded by `signal.set_wakeup_fd` or an atomic copy taken outside the
  handler) rather than acquiring `_LIVE_LOCK` inside it.

### F4. `count_reads()` raises on a corrupt/truncated `.gz` instead of reporting it
- **Severity:** medium
- **Location:** `cerberus/utils/fastq.py:38-56` (fallback at `:52-53`), `_count_python` at `:83-90`
- **What:** The docstring promises "A decompression failure is reported rather than silently
  yielding a plausible-looking number." What actually happens: `_line_count_pipe` correctly returns
  `None` and logs a warning, then `count_reads` falls through to `_count_python`, which opens the
  same broken file with Python's `gzip` and raises. `EOFError` is **not** an `OSError`, so
  `cli.main`'s `except (FileNotFoundError, PermissionError, OSError)` at `cli.py:460` does not
  catch it — the user gets a raw traceback and exit 1.
- **Trigger:** Reproduced at unit level: a truncated `.fq.gz` →
  `EOFError: Compressed file ended before the end-of-stream marker was reached`; a file with gzip
  magic but garbage payload → `gzip.BadGzipFile: Unknown compression method`. Both first log the
  intended `pigz failed (rc=1): ...` warning, then die. Reachable via `StageTracker.record()`
  (`pipelines/base.py:62-67`), `RunAccounting.add_final` (`accounting.py:44-51`), and
  `report.collect_outputs` (`report.py:123`) — i.e. from a purely observational code path, after
  all the real work has succeeded.
- **Consequence:** A diagnostics helper can abort an otherwise-finished run, and because the
  exception escapes `orchestrator.run()` the report is never written and `_work/` is left behind.
  v0.1.1 did not crash here (it silently returned the partial `wc` count) — different bug, but the
  new behaviour is a harder failure than the docstring claims.
- **Fix:** Wrap the `_count_python` fallback in `try/except (OSError, EOFError)`, log
  `"could not count %s (%s); reporting 0"`, and return `0` (or `-1`/`None` if the accounting
  schema can express "unknown"). Counting must never be able to fail a run.

### F5. `_line_count_pipe()` deadlocks if the decompressor writes more than one pipe buffer to stderr
- **Severity:** medium
- **Location:** `cerberus/utils/fastq.py:63-78`
- **What:** `p1` is spawned with `stderr=subprocess.PIPE`, but the parent calls `p2.communicate()`
  and then `p1.wait()` (`:70`) **before** reading `p1.stderr` (`:71`). Once the child fills the
  64 KB stderr pipe buffer it blocks on write, never closes stdout, `p2` never sees EOF, and
  `p1.wait()` never returns. No timeout anywhere.
- **Trigger:** Reproduced: `_line_count_pipe(["bash","-c","<300 KB to stderr>; printf 'a\\nb\\n'"])`
  hung; the probe thread was still alive after a 20 s join. In production this needs a
  decompressor that is chatty on stderr — plausible for `gzip -dc`/`zcat` over a multi-member
  archive with several bad members, which is exactly the shape Cerberus produces via
  `concat_gz`/`concat_mate_tagged`.
- **Consequence:** A hard hang with no timeout and no log line, in the counting path that now runs
  on every stage (F7). v0.1.1 did not capture stderr at all, so this hang is newly introduced.
- **Fix:** Use `p1.stderr` only via a drain, or simply merge stderr into the log:
  replace the manual two-process construction with
  `subprocess.run(cmd, stdout=PIPE, stderr=PIPE, timeout=...)` piped in Python, or read
  `p1.stderr` in a thread before `p1.wait()`. Add a `timeout=` to both waits.

### F6. `_clean_work_dir()` destroys the fastp/fastplong QC report and every stats file
- **Severity:** medium
- **Location:** `cerberus/orchestrator.py:191-192`, `:210-221`
- **What:** The new end-of-run `shutil.rmtree(cfg.work_dir)` removes `_work/` wholesale. That
  directory is not only intermediates: it holds `_work/00_qc/fastp.html` and `fastp.json` (the
  human-readable QC report, produced by `stages/qc.py:74-75`), every `bbduk` `stats=` file
  (`stages/kmer.py`, `stages/entropy.py`), and every `samtools flagstat` output
  (`stages/align.py:143`). Nothing copies them into `reports/` or `logs/` first, and the HTML
  report does not inline them.
- **Trigger:** Reproduced. After a default `--all` run, `find run_all -type f` shows 8 FASTQs, 43
  step logs and 4 report files — **no** `fastp.html`, no `fastp.json`, no `*.flagstat.txt`, no
  `*.stats.txt`. The same run with `--keep-intermediates` retains all of them.
- **Consequence:** Silent loss of the single most-requested QC artefact (`fastp.html`) on every
  default run. v0.1.1 never deleted `_work/`, so this is a straight regression; the mitigation
  (`--keep-intermediates`) also retains every BAM-derived FASTQ, so the user must choose between
  the QC report and a many-×-input disk bill.
- **Fix:** Before `_clean_work_dir()`, move/copy `fastp.{html,json}` (and `fastplong.*`) into
  `reports/`, and the `*.flagstat.txt` / `*.stats.txt` files into `logs/<stage>/`. Alternatively
  make `_clean_work_dir` prune only `*.fq.gz`/`*.bam` and leave small text/HTML artefacts.

### F7. `StageTracker.record()` + `add_final` + the report make ~5× more full decompression passes than v0.1.1
- **Severity:** medium
- **Location:** `cerberus/pipelines/base.py:62-67`, `cerberus/accounting.py:44-51`,
  `cerberus/report.py:123-124`
- **What:** `record()` calls `count_reads()` on every stage output, `add_final` counts every
  published file again, and the report counts them a third time *and* runs `_gzip_ok()` — a fourth
  full pass, in Python's `gzip`. Nothing is memoised.
- **Trigger:** Instrumented a real `--all` run (input pair 0.84 MB compressed): **58**
  `count_reads()` calls decompressing **13.1 MB** — 15.6× the input size — plus **8** `_gzip_ok()`
  passes over the published outputs, for **66 full decompressions**. Static count of the same
  configuration in v0.1.1 is ~13 (`orchestrator` 3 + `meta` 2 + `profiling` 2 + `add_final` ~6).
  Individual files are counted redundantly: `S1.meta.R1.fastq.gz` 4×, `S1.profiling.fastq.gz` 4×,
  `S1.meta.orphans.fastq.gz` 4×. Throughput measured on this box: ~1.5 s per 172 MB compressed /
  500 MB uncompressed pass when page-cached, i.e. I/O-bound on real data.
- **Consequence:** On a 100 GB paired dataset the accounting/report layer alone adds on the order
  of an hour of pure decompression, for numbers that are already known or trivially cacheable. It
  also multiplies the blast radius of F4 and F5.
- **Fix:** Memoise `count_reads` on `(resolved path, st_size, st_mtime_ns)`; have
  `report.collect_outputs` and `accounting.add_final` reuse the tracker's numbers instead of
  recounting; drop `_gzip_ok()`'s separate Python-gzip pass (the `pigz` count already proves the
  stream decompresses — derive `gzip_ok` from whether `count_reads` succeeded).

### F8. `residual_host_estimate()` never matches the profiling / long-read GDPR heads
- **Severity:** medium
- **Location:** `cerberus/pipelines/gdpr.py:208-224` (keys produced at `:171-192`)
- **What:** The function looks up the fixed keys `gdpr_input_paired`, `gdpr_after_kraken2`,
  `gdpr_after_human_kmers`, `gdpr_after_minimap2`. Those are only recorded by the *paired* branch
  (`:80-112`). `_gdpr_single()` records `gdpr_input_{label}` / `gdpr_after_kraken2_{label}` /… —
  `_merged`, `_orphans`, `_long` — which never match. Additionally, when the human k-mer asset is
  absent or `--no-gdpr-kmer-scrub` is used, `gdpr_after_human_kmers` is missing and the *minimap2*
  row is dropped too, because it is chained off that key.
- **Trigger:** Verified in the generated HTML from a real `--all` run: the "GDPR scrub —
  contribution of each mechanism" table lists only `meta_gdpr`; `profiling_gdpr` is absent
  entirely. Unit check: `residual_host_estimate({...paired keys...})` → all three mechanisms;
  `{...merged keys...}` → `{}`; paired-without-human-kmers → `{'kraken2': 10.0}` only.
- **Consequence:** For `--profiling --gdpr` and for every `--long` run, the report's headline
  "measured residual" evidence — the whole point of the GDPR head per the module docstring — is
  silently empty. And with two mechanisms instead of three, the alignment mechanism's contribution
  disappears from the report while still being applied.
- **Fix:** Build the `order` list from the labels actually present (or have `_gdpr_single` record
  the un-suffixed keys under a per-stream namespace), and chain each mechanism off the previous
  *recorded* key rather than a hard-coded one.

### F9. `concat_mate_tagged()` aborts on a zero-byte or non-gzip input and leaks `.part` files
- **Severity:** low
- **Location:** `cerberus/stages/concat.py:104-131`
- **What:** Inputs are filtered on `p.exists()` only (`:85`) — unlike the callers' `st_size > 40`
  guard — and the merge pipes each through `pigz -dc`. A zero-byte `.gz`, or a plain-text FASTQ,
  makes `pigz` exit 1 and `pipe()` raise. The `.part*` cleanup at `:124-126` runs only on the
  success path, so any parts already written are orphaned.
- **Trigger:** Reproduced: a 0-byte `.fq.gz` input → `ToolError: ... [stage 1/3: pigz]`, and
  `m3.fq.gz.part0` left on disk. Same for an uncompressed `.fq` input.
- **Consequence:** Low reach today (every upstream stage writes a valid empty gzip member — the
  `_write_empty_gzip` / `_empty_paired_passthrough` helpers are correct), but it turns a benign
  empty stream into a hard run failure, and the leaked parts survive if the exception aborts the
  run before `_clean_work_dir`.
- **Fix:** Skip inputs with `st_size <= 40` (matching `qc._has_reads`), and wrap the staging loop
  in `try/finally` that unlinks every `part` created so far.

### F10. Report's "Removed here / % removed" column diffs unrelated streams
- **Severity:** low
- **Location:** `cerberus/report.py:365-379`
- **What:** The per-stage table computes `removed = prev - s.reads` over consecutive rows of a
  mode, regardless of which stream each row describes. In `meta_gdpr` the paired rows are followed
  by the orphan rows, so the first orphan row is diffed against the last paired row.
- **Trigger:** Reproduced in `run_all/reports/cerberus_report.html`: after
  `gdpr_after_minimap2 = 8,000` the next row reads
  `gdpr_input_orphans | 0 | removed 8,000 | 100.00%`.
- **Consequence:** The report asserts a 100 % removal that never happened, in the table a reviewer
  is told to "compare against before trusting the result".
- **Fix:** Group stage rows by stream (split on the `gdpr_input_*` boundary, or carry a stream tag
  on `StageCount`) and reset `prev` at each group.

### F11. `concat_mate_tagged()` double-tags read names that already end in `/1` or `/2`
- **Severity:** low
- **Location:** `cerberus/stages/concat.py:111`
- **What:** The awk program appends the suffix unconditionally
  (`print $0 "/1"`), so `@x/1` becomes `@x/1/1`.
- **Trigger:** Reproduced at unit level (`@x/1` → `@x/1/1`, `@x/2` → `@x/2/2`). **Not** reachable
  through the pipeline as built: verified with the `half.*` fixture, whose names are `@CLEAN_0/1`
  — both minimap2 and bowtie2 strip the trailing `/1`,`/2` before the BAM, and `samtools fastq -n`
  keeps them stripped, so the merged output is correctly `@CLEAN_8/1` / `@CLEAN_8/2` with zero
  duplicate IDs.
- **Consequence:** Cosmetic today; a latent trap if the helper is ever pointed at FASTQ that did
  not pass through an aligner (or if an aligner is swapped for one that preserves the suffix).
- **Fix:** `sub(/\/[12]$/, "", $0)` before appending, in the same awk rule that strips the comment.

### F12. `publish()` degrades silently when a stage produced nothing, and `_work/` is then deleted
- **Severity:** low
- **Location:** `cerberus/pipelines/base.py:44-51`, with `cerberus/orchestrator.py:191`
- **What:** A missing `src` yields a `log.warning` and `None`. Callers store that `None` into
  `PipelineResult`, so the GDPR head silently skips the stream
  (`gdpr.py:79`, `:122`, `:141`), the report simply omits the row, and `_clean_work_dir()` then
  removes any partial evidence. v0.1.1 would have raised on `None.replace(...)` and failed loudly.
- **Trigger:** Not reproducible with the current stage set (every tool creates its output file
  even when empty), so this is a code-reading finding, not an observed one.
- **Consequence:** If it ever fires, the run reports success, the GDPR deliverable for that stream
  is missing (or a stale one from a previous run remains — see F13), and `_work/` is gone.
- **Fix:** Have `publish()` raise unless the caller opts into tolerance
  (`publish(..., required=False)`), and record a run-level warning through `accounting.warn` rather
  than only the logger.

### F13. Stale deliverables from a previous run survive a narrower re-run
- **Severity:** low
- **Location:** `cerberus/pipelines/base.py:37-51` (docstring), `cerberus/orchestrator.py:158-180`
- **What:** Nothing clears `out_dir` of files this run will not write. `publish()`'s docstring
  advertises "a `--dry-run` (or a stage that produced nothing) can never destroy the results of a
  previous real run" as a safety property, without the complementary hazard.
- **Trigger:** Reproduced: an `--all` run followed by a `--meta`-only run on *different* input into
  the same `--out-dir` leaves `S1.meta.R1.fastq.gz` = 2 000 records (new) sitting next to
  `S1.meta.R1_GDPR.fastq.gz` = 4 000 records, `S1.profiling.fastq.gz` = 8 000 and
  `S1.profiling.orphans_GDPR.fastq.gz` = 8 000, all from the previous run and all mutually
  inconsistent. The report and `accounting.tsv` list only the new outputs, so nothing flags it.
- **Consequence:** For a tool whose `*_GDPR` files are meant for publication, a stale `_GDPR` file
  that does not correspond to the data beside it is the worst possible artefact to leave lying
  around. (Same behaviour in v0.1.1 — listed because v0.2.0 now presents the non-deletion as a
